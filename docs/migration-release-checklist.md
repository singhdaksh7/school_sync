## Order

Migrations apply in filename-timestamp order automatically via
`prisma migrate deploy` — no manual ordering step needed as long as no
migration folder has been renamed/reordered out of sequence.

## Connection strings

- `DATABASE_URL` — pooled connection, used by the running app.
- `DIRECT_URL` — direct (non-pooled) connection, used only by the Prisma
  CLI for migrations (see `prisma.config.ts`: `process.env.DIRECT_URL ?? env("DATABASE_URL")`).
  If your database sits behind a pooler (PgBouncer, Neon's pooled endpoint),
  set `DIRECT_URL` to the *unpooled* connection string — some DDL operations
  are unsafe or unsupported through a transaction-mode pooler.

## Commands (in order)

```
1. Take a backup / checkpoint (platform-specific — e.g. Neon branch/snapshot).
2. Verify DATABASE_URL is the pooled connection string.
3. Verify DIRECT_URL is the direct (non-pooled) connection string.
4. npx prisma migrate status         # inspect pending migrations
5. (review the SQL of every pending migration manually)
6. npx prisma migrate deploy
7. npx prisma migrate status         # confirm clean
8. npx prisma generate
9. curl <deployed-url>/api/health?check=readiness
10. Run the application's smoke tests against the deployed environment.
```

## Invite-token hashing migration — invalidation note

The `20260704120000_hash_invite_tokens` migration changed invite lookup to
use a hash of the raw token (`tokenHash`) rather than the raw token itself.
**Any invite row created before this migration has `tokenHash = null` and
is no longer resolvable** (`SchoolInvite`/`TeacherInvite` — see the comment
in `prisma/schema.prisma`). This is by design (closing a token-exposure
risk), but it means: **any outstanding, unused invite sent before this
change stopped working** and must be resent/regenerated by the inviting
admin/Founder after this migration is applied. There is no automatic
migration of old tokens (the raw token was never stored server-side to
re-hash).

## Rollback/backup considerations

- Every migration in this project has been additive (`ADD COLUMN`,
  `CREATE TABLE`, loosened `NOT NULL` constraints) — there is no destructive
  migration to roll back in the normal sense. If a deploy needs to be
  reverted, reverting the application code is sufficient; the additive
  schema changes are backward-compatible with the previous code version
  (unused new columns/tables simply go unread).
- Take a platform-level backup/branch/snapshot before running
  `prisma migrate deploy` regardless — standard practice, not specific to
  this release.
